# parser

## Context

hook-guardian の判定は、コマンド文字列を読み、破壊的効果と対象パスを取り出すところから始まる。
いまの実装は自前の字句解析と構文解析で、レビューで見つかった欠陥（値を取るオプションの中のコマンド置換、ラッパーの値付きオプション、`bash -c` の後続引数）がすべて「走査し忘れた位置」という同じ形をしている。
利用者は、自前のパーサでは漏れが尽きない（もぐらたたきになる）として、成熟した OSS のシェルパーサに頼る方向を検討したい。シェルは bash だけではないため、対応する範囲と、読めないときの扱いも決める必要がある。
この記録は、コマンドの読み方（パーサの調達、走査の不変条件、対象シェル、実行時仲介の可否）を決めるためのもの。

Position: 実装計画のレビューを受け、解析失敗時の効果の扱いを A20 として記録し、REQ-038 の文面を採用パーサ（brush-parser）の失敗の表し方に合わせた（照合 2 回で 0 件）。実装計画（parser-rework）とあわせて承認の材料を提示した。利用者の判断待ち。

## Agreements

- A1 対象シェルは bash と POSIX sh を一次対象とする。`sh`、`dash`、`zsh`、`ksh` を `-c` で明示起動された場合は、その本体を bash 互換の文法として読む。読めない構文と、fish のような非 POSIX 系のシェルは読まずに ask にする。
  - why: エージェントの実行経路（Bash ツール）は bash であり、シェルは何でもありの領域なので、読める範囲を決めて外は ask に落とすのが安全側になる
  - decided_by: 利用者（推奨を採用）
- A2 字句解析と構文解析は、成熟した OSS の完全なシェルパーサに置き換える。自前に残すのは効果の意味論（プログラムごとの対象の決め方）とパス分類だけにする。パーサが失敗したとき、または部分解析になったときは ask にする。
  - why: 自前の部分的な文法モデルでは、走査し忘れた位置の欠陥が尽きない（もぐらたたき）。文法の網羅は実績のある実装に任せ、この製品固有の意味論だけを自前で持つ
  - decided_by: 利用者（推奨を採用）
- A3 「すべての単語・コマンド置換・リダイレクト・複合構文を、位置や役割にかかわらず 1 回ずつ訪問する」を要求として固定し、回帰コーパスで縛る。合格線は、文法要素の読みが決定的であること、読めない構文は必ず ask に落ちること、自前の文法解析がゼロであること。
  - why: 直近の欠陥はすべて同じ形（走査し忘れ）で、個別の修正では再発する。走査の完全性を不変条件としてテストで固定するのが再発防止の本体になる
  - decided_by: 利用者（推奨を採用）
- A4 実行時仲介（sandbox や syscall の遮断）は採らない。A46 のとおり、この見張りは事故を減らす柵であり、境界ではない。強制力が要る場合は kakoi 側の仕組みに任せる。
  - why: 実行前の判定という枠（PreToolUse フック）と、配布や権限の前提を変えないため
  - rejected: seccomp user notification や PATH shim で実行時に止める（柵ではなく境界になり、別アーキテクチャの製品になる）
  - decided_by: 利用者（推奨を採用）
- A5 M1 の対象シェルは A1 のとおり bash と POSIX sh とする。別のシェル（fish など）への対応は、文法を後から足せる形にする（利用者は tree-sitter-fish の存在を確認済み）。足したときも、読めない構文は ask にする。
  - why: シェルは何でもありの領域なので、対象を広げたくなったときにパーサごと作り直しにならない形にしておく
  - decided_by: 利用者
- A6 シェルの解析は `crates/guardian-parser` として分離する。この crate が OSS の文法を背後に隠し、自前の正規化した AST だけを公開する。ほかの crate は OSS の型に依存しない。対象シェルの追加（A5）は、この crate の中への文法の追加として行う。A2 と A10（crate の分割と責務）を改訂する。
  - why: 文法の差し替えや追加が 1 つの crate に閉じ、判定の意味論（core 以降）がパーサの都合から独立する
  - decided_by: 利用者
- A7 パース結果に ERROR ノードか MISSING ノードが 1 つでもあれば ask にする。読み手は「知っている形だけを読む」方式とし、AST に現れた未知のノード形も ask に落とす。
  - why: A2 の「部分解析は ask」の具体化。permissive な文法が非 bash の入力を通すため、形の検証が要る
  - decided_by: 利用者（推奨を採用）
- A8 `guardian-parser` は、すべての単語・すべての置換本体（再帰）・すべてのリダイレクト・すべての複合構文を 1 回ずつ訪問し、正規化 AST（コマンド列、効果候補の単語とリダイレクト、置換の再帰構造）を返す。core 以降はパーサ crate の型を見ない。走査の完全性は「置換ノードが正規化 AST に必ず現れる」性質テストで縛る。
  - why: 走査漏れクラスの再発防止（A3）を、crate の境界とテストの形に落とす
  - decided_by: 利用者（推奨を採用）
- A9 合格線は 4 つのコーパスで縛る。(a) bash の文法要素（コマンド列・パイプ・and/or・複合コマンド・全リダイレクト・here-doc と here-string・コマンド置換とプロセス置換・算術・`[[ ]]`・関数・`{}`・サブシェル・配列）、(b) 実測の誤ブロック 355 コマンドの再判定、(c) 読めない構文は ask の例、(d) 走査の性質テスト。読めないものは ask に落ち、自前の文法解析はゼロ。
  - why: A3 の合格線を検証可能な形にする
  - decided_by: 利用者（推奨を採用）
- A10 パーサの選定では、有名であることを根拠にせず、ライセンス・文法の忠実度・走査の形に加えて、保守状況（直近のリリースとコミット、issue や PR への応答）とサポート状況（実プロジェクトの依存、団体の関与）を調べて決める。調査は選定の前に厚く行う。
  - why: 有名でも放置されていれば選定の根拠にならない。保守とサポートを選定の基準に含める
  - decided_by: 利用者
- A11 パーサは `brush-parser` を採用する。版を固定（`=0.4.0`）し、入力サイズと再帰の深さに上限を設け、パースは `catch_unwind` で包んで panic は ask に落とす。DoS の修正（#1416）を含むリリースが出たら版を上げる。置換本体は文字列で返るため再帰的に読み直し、各段で読めなければ ask にする。次点は `tree-sitter-bash`（採る場合は #343・#348 を載せた fork が前提）、三番目は `mvdan/sh`（Go 境界は最後の手段）。
  - why: 有名さではなく、実際の保守（毎日の活動、DoS 修正が 3 日で入った）とサポート（Zed などの実依存）で選んだ。中身の差し替えは `guardian-parser` の I/F（A6・A8）が保証する
  - decided_by: 利用者
- A12 入力の上限は固定値で仕様に書く。コマンド文字列は 1 MiB、入れ子と置換の再帰の深さは 128 段を超えたら ask にする。設定キーには出さない（必要になったらその時に検討する）。
  - why: DoS 防御の挙動を先に固定する。値は実測で見直す余地を残す
  - decided_by: 利用者（推奨を採用）
- A13 レビューの指摘を受け、"check" の JSON に最上位の "reason"（判定の理由）を足す。効果が無い ask（構文を読めない、読めないシェル、入力が大きすぎる）でも理由が機械可読に残るようにする。効果ごとの "reason" はそのままとする。
  - why: 最もよく出る拒否の経路の理由が JSON に残らない
  - decided_by: 利用者（レビューの指摘に基づく明示化）
- A14 読めない構文などの構文解析由来の ask は、ほかの効果の判定と最悪値で合成し、より重い block があればそれが勝つ（REQ-009 と同じ）。
  - why: 構文解析の ask が block を上書きすると、読める保護削除を見逃す（m1 のレビューで見つかった退行と同じ形）
  - decided_by: 利用者（REQ-009 の適用の明示化）
- A15 別シェルの文法の追加（REQ-040、EX-051）は M1 では作らない（deferred）。`guardian-parser` の口（A6）は M1 に含める。
  - why: 追加の文法はまだ無く、M1 の対象は bash と POSIX sh（A1）。拡張の口だけを先に用意する
  - decided_by: 利用者（A5 の範囲の明示化）
- A16 シェル起動の認識は次のとおり。(1) bash 系のシェル（"bash"、"sh"、"dash"、"zsh"、"ksh"、"mksh"。ラッパーを外した後の basename で見る）で引数に "-c" を含む起動（"-lc" のようなまとめ書きを含む）は、その次の語を本体として bash 互換の文法で読む。(2) "-c" を伴わない起動（"bash script.sh"、"sh < file"）は、本体がコマンド文字列の外にあるため読まず、通常のコマンドとして判定する。(3) 知っている非 POSIX 系のシェル（"fish"、"csh"、"tcsh"、"elvish"、"xonsh"、"nu"、"pwsh"）は、本体の有無にかかわらず ask にする。(4) 知らないプログラムはシェルとみなさない。(5) 認識はラッパー（sudo と doas）を外した後のプログラムの語で行う。
  - why: "-c" の本体だけがコマンド文字列の中にある。ファイルや標準入力の本体は判定の外（旧フックと同じ境界）にし、読まないと決めたシェルで実行しようとする場合は ask に落とす
  - decided_by: 利用者（推奨を採用）
- A17 字句解析は、判定の経路と、設定の照合（見張りの例の分割と、カスタムルールの本文の引用の除去）で共有する。
  - why: 引用の解釈が 2 つに分かれると、同じ文字列が別々に分割されて判定が食い違う
  - decided_by: 利用者（レビューの指摘に基づく明示化）
- A18 入力の上限は、サイズを構文解析の前に測り（置換の再帰読みでは累計で測る）、深さを再帰の各段で、深くなる前に測る。
  - why: 深くなってからでは遅く（スタックオーバーフローは捕まえられない）、累計で測らないと置換を並べた入力で上限を回避できる
  - decided_by: 利用者（レビューの指摘に基づく明示化）
- A19 正規化した構文木が保つものは次のとおり。コマンド列の順序と区切り（";"、"&&"、"||"、パイプ）、プログラムと引数の語（順序、引用の状態、語の断片、置換の本体）、リダイレクトの種類（読み、書き、追記、切り詰め、読み書き、複製）と対象の語とファイル記述子、複合構文（条件、繰り返し、グループ、サブシェル、関数）の本体。
  - why: core 以降が依存する契約を明示する
  - decided_by: 利用者（レビューの指摘に基づく明示化）
- A20 構文解析が失敗した命令からは、その効果を取り出さない（読めない部分は ask の原因になり、読めている部分の効果だけが残る）。A7 の「ERROR ノードか MISSING ノード」は、採用した `brush-parser` では解析の失敗（Err）として現れる。
  - why: 採用したパーサの失敗の表し方に合わせる。プログラムが何か分からないまま引数を削除の対象とみなすと、読めない命令を block にしてしまう
  - decided_by: 利用者（A7 の採用パーサへの対応づけ）
