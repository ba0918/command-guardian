# OpenCode V2のstandalone実行への対応

## Context

`opencode run --standalone` は共有の管理サービスを使わず、専用のサーバーを立てて動く。
プラグインの自動接続は管理サービスの登録PIDと自身のPIDの一致を求めるため、standaloneでは接続できない。
接続できないとshellの判定が"/unknown-shell"のままになり、コマンドの中身にかかわらずすべての実行が判定不能から承認要求へ進み、承認の経路も無いため実行が止まる。
docs/opencode.mdはstandaloneに明示の接続設定を求めているが、下の調査で、その設定ではstandaloneに接続できないと分かった。
どの実行を通し、承認をどこで扱うかを決める必要がある。
また、プラグインはOpenCodeが2.0.21でなければshellの実行ごとに例外を出し、自動接続も2.0.21の相手だけを採用するため、OpenCodeを更新するとプラグインが使えなくなる。この版の扱いも合わせて決める。

Position: 第1ラウンドでA1・A2を決定した。第2ラウンドでA3・A4、第3ラウンドでA5〜A9を決定した（すべて推奨を採用）。IRを記述し、敵対的レビューの指摘から第4ラウンドでA10〜A15を決定し、照合の2回目を実行中。利用者の判断で、OpenCodeの版の扱いもこの記録で決めることにし、第5ラウンドでA16〜A19、第6ラウンドでA20を決定した。未決定は無い。照合を3回行い、仕様は承認・コミット済み。計画の検討中に、evaluateフックが呼ばれない入力があり承認に回せないと分かり、A21で接続が無いときの扱いを改め、第8ラウンドでA22・A23を決定した。IRを改訂し、敵対的レビューの指摘から第9ラウンドでA24〜A26を決定した。未決定は無い。照合を2回で完了した（未裏付け0件）。承認待ち。

  - decided_by: 利用者（推奨を採用）
- A2 承認の経路が無くても、shellを確かめられる限り判定を行い、allowは実行し、blockは拒否する。承認の経路が無いことの影響はaskの実行だけに限る。
  - why: 承認の経路が無いことでshellの判定まで止まり、すべての実行が判定不能になる現在の欠陥を解消するため
  - decided_by: 利用者（推奨を採用）

- A3 接続が無いときに判定がaskになった実行は、プラグインの権限のevaluateフックでOpenCode自身の承認要求として出し、返答があるまで起動させない。"run --auto"による自動承認は有効な承認として扱う。
  - superseded_by: [接続が無いときはOpenCodeに委ねる](#A21)
  - why: standaloneの"--auto"では利用者案（OpenCodeに任せる）と同じ結果になり、管理サービスを無効にしたTUIのように人が使う場面では確認が残り、OpenCodeが許可していてもguardianのaskは承認を求めるREQ-049・REQ-050をstandaloneでも保てるため
  - rejected: guardianは承認を求めずOpenCodeの規則だけに任せる案、それをmode.defer_askが有効なときだけにする案
  - decided_by: 利用者（推奨を採用）
- A4 接続が無いときは、shellのcreate.beforeフックが受け取る実際のshell、cwd、コマンドで判定し、"/unknown-shell"で判定しない。
  - why: 起動される入力そのものを判定するので、判定と起動の一致（REQ-047）を満たせるため
  - decided_by: 利用者（推奨を採用）

- A5 他のプラグインの権限のevaluateフックがguardianの結果を上書きしないことを対応条件に加え、導入手順に記載する。上書きされた場合の振る舞いは保証に含めない。
  - why: プラグイン同士の呼び出し順はguardianから決められず、固定版でも順序を確認できていないため
  - decided_by: 利用者（推奨を採用）
- A6 接続が無いときにaskと判定した実行が、OpenCodeの承認に回って返答を得たことを確かめられないまま起動に進む場合は、理由を示して実行しない。
  - superseded_by: [接続が無いときはOpenCodeに委ねる](#A21)
  - why: 承認の経路が使えないときは実行しないREQ-052の扱いを、コマンドが解析されない入力などでも保つため
  - decided_by: 利用者（推奨を採用）
- A7 管理サービスや明示の接続設定で接続できる場合は、従来のHTTPの承認の経路を使い、新しい経路は接続が無いときだけ使う。
  - why: 検証済みの経路を変えず、変更を最小にするため
  - decided_by: 利用者（推奨を採用）
- A8 standaloneの検証は、固定版2.0.21を`serve --stdio`でモデルなしに隔離して起動し、allowの実行、blockの拒否、askが承認の返答まで起動しないこと、拒否の返答で実行しないこと、承認に回らなかったaskが止まることを確かめる。"run --standalone"の通し実行は必須にしない。
  - why: 通し実行にはモデルが要り、standaloneと同じ起動経路をモデルなしで再現できるため
  - decided_by: 利用者（推奨を採用）
- A9 standaloneに明示の接続設定を求める案内（プラグインのエラー文面とdocs/opencode.md）を改め、standaloneは接続設定なしで動くと説明する。
  - why: standaloneのパスワードは実行ごとの乱数で、明示の接続設定では接続できないため
  - decided_by: 利用者（推奨を採用）

- A10 接続が無いときも、判定不能（REQ-051）、Bash以外のshell（REQ-055）、判定と起動の一致を確かめられない場合（REQ-047）は、askと同じくevaluateフックの経路でOpenCode自身の承認に回し、それぞれの理由を付ける。
  - superseded_by: [接続が無いときはOpenCodeに委ねる](#A21)
  - why: これらは接続があるときにOpenCodeの承認に渡す扱いであり、接続の有無で意味を変えないため

  - superseded_by: [接続が無いときはOpenCodeに委ねる](#A21)
  - why: 並行した実行で別の実行の判定を使うと、askの実行が承認なしで起動しうるため
  - decided_by: 利用者（推奨を採用）
- A12 OpenCodeの承認に"always"が返った場合は、OpenCodeの標準の扱いに従い、それによって承認待ちの他の実行が承認されることを妨げない。以後の新しい実行には、REQ-050のとおりguardianの承認要求を出す。
  - superseded_by: [接続が無いときはOpenCodeに委ねる](#A21)
  - why: "always"は利用者自身が選んだ操作であり、その結果は利用者の責任とするため
  - rejected: "always"でも承認待ちの他の実行にそれぞれの返答を求める案
  - decided_by: 利用者
- A13 接続オプションが未指定なら、管理サービスの登録が無い場合も、登録の検証に失敗した場合も、接続が無いときの経路に入り、登録に書かれた宛先へは通信しない。接続オプションを明示して失敗した場合だけ、従来どおり実行しない。
  - superseded_by: [明示した設定の失敗も止めない](#A22)
  - why: 従来の停止は別のサーバーへ承認や認証情報を送らないためであり、新しい経路はプロセス内で完結してどこにも送らないため。管理サービスの横でstandaloneを使うとPIDの合わない登録が残り、停止すると欠陥が直らないため
  - decided_by: 利用者（推奨を採用）

  - superseded_by: [接続が無いときはOpenCodeに委ねる](#A21)
  - why: 接続があるときの検証（REQ-058）とそろえるため
  - decided_by: 利用者（推奨を採用）

  - superseded_by: [接続が無いときはOpenCodeに委ねる](#A21)

  - why: 更新の速いツールで版の一致を求めると、更新のたびにプラグインが使えなくなるため。版の一致は安全に寄与せず、守るべきはプラグインが頼る振る舞いであるため

  - decided_by: 利用者（推奨を採用）

  - decided_by: 利用者（推奨を採用）

## Investigation

固定版2.0.21のコードと、モデルを呼ばない実測で確かめた事実である。

- standaloneは子プロセスで`opencode serve --stdio --port 0`を起動し、プラグインはその子の中で動く。待ち受けは127.0.0.1の任意ポートで、認証は実行ごとの乱数のパスワードである。
- stdioモードは環境変数のパスワードを消し、管理サービスの登録を書かない。プラグインの文脈にはHTTPのクライアント、URL、認証情報、設定のAPIが無い。そのため明示の接続設定（serverUrl、passwordEnv）でもstandaloneには接続できない。
- 管理サービスを設定で無効にした場合も同じ起動経路を使う。
- shellのcreate.beforeフックは、権限の確認と起動より前に、実際に使うshell、cwd、コマンドを受け取る。
- プラグインの権限のevaluateフックは、規則と保存済みの許可を適用した後に呼ばれ、結果をaskにすると、ホストは返答があるまで起動を待つ。規則がdenyなら、フックより前に拒否される。
- "run"は、自分のセッションの承認要求に、"--auto"ならonceで、そうでなければrejectで返答する。standaloneかどうかで変わらない。
- 未確認：複数のプラグインのevaluateフックの順序（後のフックが結果を上書きできるか）、コマンドが一つも解析されない入力でevaluateが呼ばれない場合の扱い。
