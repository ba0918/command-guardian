# LLM 助言層の検討

## Context

利用者は、一通りの機能を実装した後のガードレールの安全性を改善するため、TODO の2層化を検討したいと依頼した。
TODO の候補は、機械判定の ask を LLM に渡す助言層であり、既定オフ・利用者設定のみ・失敗時は機械判定へ戻す・tighten-only を既定とする案が記されている。
現在の判定経路は、解析結果・対象パスの観測・設定規則を合成して Report を返す。
ask だけを対象にする案では、機械判定が allow とした見逃しを再検査しないため、改善したい安全性と検査対象の関係を先に決める必要がある。

Position: Q36まで確認済み。仕様草稿の独立レビューと出典照合を完了し、利用者の承認待ち。文書形式と参照のエラーはなく、実装待ちの試験不足と既存文書の行数通知は残る。実装、コミット、実モデルの呼び出しは未実施。

## Agreements

- A1 主目的は、機械判定が allow にした危険な操作の見逃しと、ask のまま承認に委ねられる危険な操作を減らすこととする。安全な操作の不要な確認を減らすことも検討対象に含める。
  - why: 利用者は A・B が主だが C もありえると回答した
  - decided_by: 利用者
- A2 承認フロー自体を減らすことを目指し、人間がすべての確認を慎重に判断する前提には置かない。
  - why: 利用者は実際には適当に承認されると述べ、承認フロー削減が実態の目的だと説明した
  - decided_by: 利用者
- A3 LLM の検査対象は、機械判定が allow または ask としたコマンドの両方とする。
  - why: 機械判定が効果を拾わなかった操作も検査するため
  - decided_by: 利用者（第2ラウンドの推奨を採用）
- A4 機械判定の block を LLM で解除しない。
  - why: LLM の誤判断で機械判定の拒否を解除する経路を作らないため
  - decided_by: 利用者（第2ラウンドの推奨を採用）
- A5 ask から allow への変更は、確認理由を限定して許す。利用者が明示的に確認を要求した規則は解除せず、解析不能や対象パス不明は LLM が安全そうと判断するだけでは解除しない。解除可能な理由は後続ラウンドで個別に決める。
  - why: 確認を減らしつつ、根拠が足りない機械判定を LLM の印象だけで許可しないため
  - decided_by: 利用者（第2ラウンドの推奨を採用）
- A6 外部モデルへ送る情報は、コマンド本文・作業ディレクトリ・機械判定の結果と理由に限定する。ファイル内容、会話履歴、環境変数一覧は送らない。
  - why: 判断に使う情報を絞り、機密漏洩と入力内の指示による判定誘導のリスクを増やしすぎないため
  - decided_by: 利用者（第3ラウンドの推奨を採用）
  - superseded_by: [A22](./2026-10-03-llm-advice-layer.md#A22)
- A7 秘密らしい値を検出した場合は外部モデルへの送信を見送る。秘密検出に完全な保証がないことを前提とする。
  - why: コマンド本文にも秘密が入り得るため
  - decided_by: 利用者（第3ラウンドの推奨を採用）
- A8 LLM のタイムアウト・通信失敗・不正な応答では元の機械判定に戻す。
  - why: 障害によって作業や確認を増やさず、現在の機械判定を最低限の守りとして残すため。元が allow なら LLM の再検査なしで通ることを含めて採用した
  - decided_by: 利用者（第3ラウンドの推奨を採用）
- A9 対象データの価値が不明であることによる ask の解除は、利用者が事前に指定した使い捨て対象の範囲に限る。LLM がコマンドやパス名から生成物らしいと推測するだけでは解除しない。
  - why: 利用者は、作業領域内のテキストファイルが重要かどうかは分からず、利用者が事前に明示するしかなさそうと説明した
  - decided_by: 利用者（第4ラウンドの推奨を採用）
- A10 LLM が危険性を判断しきれない場合は元の機械判定を維持する。危険な操作だと判断した場合は block とし、不確実というだけで新しい ask を増やさない。
  - why: 判断材料が足りないことと危険と判断したことを分け、承認フローを増やさないため
  - decided_by: 利用者（第4ラウンドの推奨を採用）
  - superseded_by: [A25](./2026-10-03-llm-advice-layer.md#A25)
- A11 初期導入の使い捨て対象の事前指定は既存の allowed_roots を使い、確認削減は機械判定側で行う。初期の LLM 層は判定を厳しくするだけとし、ask から allow への変更は既存設定では表現できない具体例が出るまで導入しない。
  - why: 利用者が決めた許可を LLM の判断に依存させず、新しい条件付き指定を現時点では追加しないため
  - decided_by: 利用者（第5ラウンドの推奨を採用）
- A12 LLM 層は利用者が指定した外部コマンドを呼び、JSON を標準入力で渡し、判定を JSON で受け取る。初期導入では guardian に TypeSafe 接続を内蔵しない。
  - why: 接続先固有の HTTP・認証・契約を guardian から分離して差し替え可能にするため。外部アダプターの導入と、参考実装との入出力調整が必要なことを含めて採用した
  - decided_by: 利用者（第6ラウンドの推奨を採用）
  - superseded_by: [A30](./2026-10-03-llm-advice-layer.md#A30)
- A13 LLM の待ち時間は上限2秒・再試行なしとし、既存の判定全体の5秒上限の残時間内で待つ。残時間が短ければその時間で打ち切って機械判定に戻す。
  - why: コマンド実行前の待ち時間を制限するため。2秒は参考実装と同じ初期値で、十分かどうかは実測が必要
  - decided_by: 利用者（第6ラウンドの推奨を採用）
  - superseded_by: [A15](./2026-10-03-llm-advice-layer.md#A15)
- A14 通常100ms未満という応答目標は LLM 無効時に維持し、LLM 有効時はモデル応答待ちを含む別の計測として扱う。
  - why: allow も検査するため、通常のコマンドでもモデル応答待ちが発生するため
  - decided_by: 利用者（第6ラウンドの推奨を採用）
- A15 LLM の timeout は設定可能とする。A13 の固定2秒上限を置き換える。それ以外の再試行なし・既定値2秒の方針は維持する。設定値と既存の判定全体の5秒上限との関係は追加で確認する。
  - why: 利用者が timeout は設定可能なものとする、と指定したため
  - decided_by: 利用者
- A16 機械判定は従来の5秒上限を維持し、LLM の待ち時間は別枠の設定可能な timeout とする。既存の判定全体で5秒という仕様はこの区分に改訂する。
  - why: 設定した LLM timeout が既存の判定の残時間で切られず、そのまま意味を持つようにするため。合計の待ち時間が増えることを含めて採用した
  - decided_by: 利用者（第7ラウンドの推奨を採用）
- A17 LLM 層の基本理念は、機械検出が難しい部分について、利用者に害を及ぼす不可逆な操作かどうかを判定することとする。
  - why: 利用者が第8ラウンドで基本理念を明示したため
  - decided_by: 利用者
- A18 LLM 層は既定オフ・利用者設定のみとする。最初は観測モードを推奨し、遮断モードへの切り替えは利用者が明示する。観測モードは LLM を呼ぶが機械判定を変更しない。プロジェクト設定では有効化や接続先変更をできなくする。
  - why: 未評価の誤遮断が直ちに作業へ影響しないようにし、クローンしたプロジェクトからモデル呼び出しや接続先を変更できないようにするため
  - decided_by: 利用者（第8ラウンドの推奨を採用）
- A19 不可逆という理由だけでは、利用者が使い捨てと指定した範囲だけを削除する操作を LLM で遮断しない。指定外への削除など、別の有害な効果は検出対象とする。
  - why: 利用者の事前指定を尊重し、不可逆性だけで既知の使い捨て対象の削除を誤遮断しないため
  - decided_by: 利用者（第9ラウンドの推奨を採用）
- A20 初期から、DB の全データ削除、クラウド資源の一括削除、秘密情報の外部送信など、ローカルファイル以外の有害な不可逆操作も検査対象とする。コマンドと機械判定から読み取れる範囲で検査し、見えていないデータの重要性や接続先の実態は推測しない。判断材料が足りなければ元の判定を維持する。
  - why: 基本理念をローカル操作に限定しないため。利用者は SQL を直接書いて DB に実行するコードも危険の具体例として挙げた
  - decided_by: 利用者（第9ラウンドの推奨を採用）
- A21 SQL の危険性は文脈による。利用者が特定テーブルの特定ユーザのデータ削除を指示した場合、DELETE を使うこと自体は不自然ではない。DROP DATABASE は危険すぎる操作の具体例とする。
  - why: 第10ラウンドの提案に対し、利用者が操作の文脈と SQL の種類を区別したため。全件削除・更新を接続先不明なら一律に危険判定するという Q16 の推奨は採用していない
  - decided_by: 利用者
- A22 外部モデルへの送信範囲は A6 のコマンド本文・作業ディレクトリ・機械判定の結果と理由に、取得元を確認できる当該操作に関係する利用者指示の必要な範囲を追加する。会話全体・ファイル内容・環境変数一覧は送らず、エージェントの自己申告を利用者指示と区別する。指示を取得できない場合は文脈なしと明示し、承認があったとは仮定しない。
  - why: 利用者が指示した対象・範囲と実際の操作を照合するため
  - decided_by: 利用者（第11ラウンドの推奨を採用）
  - superseded_by: [A27](./2026-10-03-llm-advice-layer.md#A27)
- A23 Codex では確認が必要で迷う場合は deny とし、実行は利用者自身の手動操作に委ねる。
  - why: 現在の Codex hook には ask を確認として届ける出口がないため
  - decided_by: 利用者
  - superseded_by: [A24](./2026-10-03-llm-advice-layer.md#A24)
- A24 Codex 向け hook は現在の写像を維持する。最終判定が allow または ask なら無出力とし、Codex 本来の承認・実行設定に委ねる。block の場合だけ理由付き deny を返す。ask を deny に変換して手動実行に委ねる A23 は採用しない。
  - why: 現在の挙動と ask 全体を deny に変えた場合の利便性への影響を確認後、利用者が Codex に委ねると回答したため。自動実行設定では ask が確認されずに通り得るという説明を踏まえて選んだ
  - decided_by: 利用者
- A25 DROP DATABASE などの重大操作でも、取得元を確認できる具体的な利用者指示と対象・操作範囲が一致する場合は ask とする。指示範囲を超える危険な操作は block とする。LLM が危険性を判断しきれない場合は元の機械判定を維持し、不確実というだけで新しい ask を増やさない。機械判定の block は解除せず、Codex の ask は A24 の写像を維持する。
  - why: 正当な重大操作を一律に拒否せず、通常の操作とは分けて実行対象を再確認するため
  - decided_by: 利用者（残件1の推奨を採用）
  - superseded_by: [A37](./2026-10-03-llm-advice-layer.md#A37)
- A26 利用者指示の範囲と鮮度を区別する。参照を含む短い指示だけから承認対象を推測せず、古い指示や別操作への承認を流用しない。参照先を取得できなければ文脈不足として扱う。
  - why: 利用者が残件2の推奨を採用したため。直近の数件の発言を拾う案も提示されたが、その具体的な範囲は未決
  - decided_by: 利用者
- A27 文脈は当該実行に先行する直近3往復を上限に、利用者発言とエージェントの返答を拾う。件数は設定可能とする。A22 の送信範囲にこの限定した文脈を加える。発言者を区別し、エージェントの返答は参照先の理解にだけ使い、承認済みという自己申告を単独の承認根拠にしない。ツール出力・ファイル本文は対象外とし、会話全体や環境変数一覧は送らない。文脈を取得できなければ文脈なしと明示する。取得できても範囲外の参照や省略された制約があり得るため、承認範囲が完全に分かったとは扱わない。
  - why: それで・その案で実行して、などの参照先を理解するために必要な返答を含めつつ、送信範囲と根拠の使い方を制限するため
  - decided_by: 利用者（Q20 の推奨を採用）
- A28 guardian 側の外部コマンド契約を先に確定し、ba-toys 側の対応は別作業とする。参考実装の現在の判定を、指示に一致する重大操作や判断不能へ無理に読み替えない。
  - why: 利用者が Q21 の推奨を採用したため。接続方式自体は、その後に提示されたクレート型プラグインとの比較を踏まえて再検討中
  - decided_by: 利用者（Q21 の推奨を採用）
  - superseded_by: [A30](./2026-10-03-llm-advice-layer.md#A30)
- A29 LLM の観測ログは、既定ではコマンド・文脈の本文を残さず、判定・理由分類・処理時間・失敗種別を記録する。調査用の本文記録は利用者が明示的に有効化するデバッグ用オプションとする。
  - why: 秘密や会話内容の蓄積を既定動作にせず、必要な調査では本文を確認できるようにするため
  - decided_by: 利用者（Q22 の推奨を採用し、デバッグ用オプションを提案）
- A30 モデル接続は Rust trait と接続クレート方式とし、接続先の追加には guardian の再ビルドが必要であることを許容する。A12 の外部コマンド方式と A28 の外部コマンド契約の先行案を置き換える。動的ライブラリの読み込み機構は作らない。単一バイナリで配布し、guardian 側で質問と判定合成を持ち、接続実装は分離する。参考実装の既存判定を無理に読み替えない方針は維持する。
  - why: 利用者は契約に合わせる手間が外部コマンドでも接続クレートでも大きく変わらないと指摘し、型で契約を共有して単一バイナリで配布する案を採用したため
  - decided_by: 利用者（Q23 の推奨を採用）
- A31 モデル呼び出しは同一バイナリの子プロセスで行い、親が設定された待ち時間を打ち切って元の機械判定に戻す。配布するバイナリは1つとする。HTTP クライアントの timeout だけに頼らない。子プロセスの終了は、すでに送った外部リクエストや課金の取消しを保証しない。
  - why: 接続クレートが timeout を守らなくても guardian が待ち続けないようにするため
  - decided_by: 利用者（Q24 の推奨を採用）
- A32 初期接続実装は TypeSafe を1つ用意する。参考実装のモデル呼び出し部分の再利用可否を確認し、質問・判定合成は guardian 側に置く。ba-toys 本体の変更は今回含めない。
  - why: 既存の参考実装と近い接続先から始めつつ、今回決めた判定の意味を guardian 側で扱うため
  - decided_by: 利用者（Q25 の推奨を採用）
- A33 初期の LLM 層は現在の Claude Code・Codex・OpenCode を対象とする。文脈取得の対応状況をエージェントごとに明示し、取得できない版・実行では文脈なしとして判定する。
  - why: 現在の対応エージェントで同じ追加検査を使えるようにしつつ、取得できない文脈を仮定しないため
  - decided_by: 利用者（Q26 の推奨を採用）
- A34 1判定のモデル呼び出しは最大1回・再試行なしとする。送信量の上限は設定可能とし、初期値を64 KiBとする。超過時は黙って本文を切り詰めず、LLM 検査を見送って機械判定に戻す。日次・月次の予算集計は初期実装に追加せず、月額の制限はサービス側に委ねる。
  - why: 費用と送信量を制限し、切り詰めで危険な部分や指示の条件を失うことを避けるため
  - decided_by: 利用者（Q27 の推奨を採用）
- A35 モデルが返す確率に設定可能な介入閾値を設け、既定は暫定的に0.9とする。危険性や指示との一致は別々に評価し、必要な判断が閾値を満たさなければ機械判定を維持する。0.9は実際に90%正しいという保証ではなく、評価前の初期値とする。
  - why: 不確実な回答で誤遮断や不要な確認を増やさず、実際の評価に合わせて調整できるようにするため
  - decided_by: 利用者（Q28 の推奨を採用）
- A36 モデルは基本 latest を使い、利用者が任意のモデル名に変更できるようにする。モデル版を固定し更新を利用者の明示操作に限定する案は採用しない。
  - why: 利用者が Q29 の推奨を修正し、基本 latest で任意に変更できれば問題ないと回答したため
  - decided_by: 利用者
- A37 DROP DATABASE のような重大操作の危険性の判断が介入閾値を満たす場合、利用者指示を取得できなくても block とする。取得元を確認できる具体的な利用者指示と対象・操作範囲の一致も確認できた場合だけ ask とする。危険性自体が不確実なら元の機械判定を維持する。指示範囲を超える危険な操作は block とし、機械判定の block は解除せず、Codex の ask は A24 の写像を維持する。A35 の必要な判断は分岐ごとに扱い、重大操作の遮断に指示との一致の判定を必須にはしない。
  - why: 危険性が不明である場合と利用者指示が不明である場合を区別し、文脈取得の失敗で明確な重大操作を通さないため
  - decided_by: 利用者（Q30 の推奨を採用）
- A38 デバッグ用の本文ログでも検出した秘密の値は伏せて記録する。通信エラーの本文などもそのまま記録しない。秘密検出時は A7 に従い外部送信を見送る。秘密検出は完全ではないため、デバッグログは機密を含み得るものとして扱う。
  - why: 調査材料を残しつつ、検出できた秘密の値をログへ保存しないため
  - decided_by: 利用者（Q31 の推奨を採用）
- A39 文脈の取得はエージェントが管理する会話データを優先し、必要な場合だけ専用キャッシュを持つ。セッションごとに取得範囲を限定し、利用者だけが読める権限にする。有効期限は設定可能・既定24時間とし、期限切れは利用せず次回アクセス時に削除する。
