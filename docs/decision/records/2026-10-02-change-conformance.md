# 変更とIRの照合の導入

## Context

実装精査の結果をIRへ取り込むには、差分ごとに既存要求内か仕様判断が必要かを記録する必要がある。
利用者は精査結果のmainへの統合後に、kotowari changesの導入を依頼した。
自動的な現状追認は行わず、実装者と独立レビュー担当の判断を別の記録として検証する。
今回の導入は開発時の検証手順であり、製品の受理入力や判定契約は変更しない。

## Agreements

- A1 製品コード、試験、ビルド設定、フック、CI、プロジェクトのエージェント指示を変更照合の対象にし、生成されたCargo.lockは対象列挙から除外する。実装者と独立レビュー担当の現在の比較記録を別々の固定ファイルに保持する。
  - why: 試験だけでなく意味に影響する実装と検証手順も照合し、生成物の変更は元の設定の判断で扱う。
  - decided_by: 導入依頼の範囲で実装者が決定
- A2 統合前にブランチ全体の比較元と候補先を呼出元が確定し、checkとreview段階のchangesおよび既存の製品チェックを必須にする。pre-commitにはchangesを追加せず、CIの公開は別の承認で行う。
  - why: 中間コミットごとに最終記録を要求せず、統合対象の全変更について独立した判断を確認する。ローカル導入だけで外部への公開範囲を広げない。
  - decided_by: 導入依頼の範囲で実装者が決定
- A3 仕様の穴への具体的なIR追加は承認範囲と根拠のある場合だけ行い、既存要求の変更・削除や根拠のない意味変更は利用者へ確認する。
  - why: 逆方向の取り込みを許しても、現在の実装を無条件に正しい仕様と扱わないため。
  - decided_by: 導入依頼の範囲で実装者が決定
