# 版の表示と0.3.0の残件

## Context

command-guardianには自分の版を表示する手段が無く、導入した版をバイナリから確かめられない。
0.3.0の統合後に、OpenCode連携の残件（明示した接続の確認が読み込み時の1回だけ、承認要求の作成失敗時の後片付けが他の承認待ちを巻き込みうる、試験が再接続の回数を固定している）、決定記録の状態の行の古さ、紹介ページの生成時の警告、FLAG-002が残っている。
利用者は、版の表示と残件をまとめて0.3.1として出すことを求めた。

Position: 第1ラウンドでA1〜A4、第2ラウンドでA5〜A8を決定した。紹介ページの警告の原因を調査中。

## Agreements

- A1 一番上で"--version"と"-V"を受け付け、標準出力に"command-guardian <版>"の1行を出し、終了コード0で終わる。設定と標準入力は読まない。版はCargo.tomlの版をそのまま使う。
  - why: 導入した版をバイナリから確かめられるようにするため。版の正本を1か所に保つため
  - decided_by: 利用者（推奨を採用）
- A2 "check"や"hook"の後ろの"--version"は版の表示として受け付けない。
  - why: "check"では"--"以降をコマンド文字列として扱う決まりがあり、ぶつかりやすいため
  - decided_by: 利用者（推奨を採用）
- A3 トップレベルのヘルプに"--version"と"-V"の案内を加える。
  - why: ヘルプが各入口のオプションを案内する決まり（REQ-045）に合わせるため
  - decided_by: 利用者（推奨を採用）
- A4 版の表示と0.3.0の残件の対応を、まとめて0.3.1として配布する。
  - why: 版が分からない問題をすぐ解き、残件も同じ配布で片付けるため
  - decided_by: 利用者
- A5 接続オプションを明示して接続や認証に失敗した状態では、実行のたびに接続を1秒で打ち切って確かめ直す。つながればその実行から通常の承認の経路を使い、つながらなければ従来どおり警告してOpenCode自身の権限判断に委ねる。
  - why: 読み込み時の一度の失敗で、そのセッションの間ずっとguardianの確認が失われるのを避けるため。待ちが生じるのは失敗している間だけである
  - decided_by: 利用者（推奨を採用）
- A6 承認要求を作れなかったものとして扱うとき（作成の失敗と、作成の応答を受け取れない場合）は、その要求への拒否の返答を送らない。
  - why: 作成が成功していた場合、拒否の返答は同じセッションの他の承認待ちもまとめて拒否しうるため。残ったguardianの確認への返答は従来どおり何もしない
  - decided_by: 利用者（推奨を採用）
- A7 再接続の試験は、つなぎ直しを試みたことを確かめ、試行の回数は固定しない。
  - why: 仕様は回数を定めておらず、試験が仕様に無い値を固定しないため
  - decided_by: 利用者（推奨を採用）
- A8 次の3つを今も有効な決まりとして守る。導入手順は、自身の管理サービスへの自動接続と、それ以外の同一HTTPサーバーへの明示的な接続・認証設定を示す。自動接続で接続できたときも、allow、block、承認待ちは明示設定で接続したときと同じように働く。接続と認証を明示した場合は、承認要求をその接続と認証で作る。
  - why: FLAG-002で、これらを述べる要求と例の出典が置き換えられた決定にしか無いと分かったため。内容は現在の実装と文書の振る舞いのとおりで、意味は変えない
  - decided_by: 利用者（推奨を採用）
