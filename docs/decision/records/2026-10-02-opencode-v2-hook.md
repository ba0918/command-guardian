# OpenCode V2 hook

## Context

command-guardian の既存のエージェント連携は Claude Code と Codex を対象とし、OpenCode V2 の連携は定義していない。
利用者は OpenCode V2 を日常的に使っており、その環境への対応を追加するために仕様の壁打ちを始めた。
調査では V2 2.0.21 のツール実行前、shell 起動前、権限評価の接続口を確認したが、guardian との実機連携は未検証である。
権限評価の入力は解析後のコマンド資源であり、元のコマンド全文と cwd を含まず、すべての shell 入力で権限評価が呼ばれるわけではない。

Position: Q1〜Q24の回答を仕様草稿へ反映済み。機械検査の文書形式・参照エラーは0件、未実装のテスト不足は31件。独立仕様レビューと最終出典照合は指摘なし。仕様全体の承認待ち。製品コードの実装は未着手。

## Agreements

- A1 OpenCode V2 へのエージェント連携の追加を仕様検討の対象とする。
  - why: 利用者が普段使うエージェント環境で command-guardian の判定を利用できるようにするため
  - decided_by: 利用者
- A2 対象はエージェントの shell ツール実行とし、通常実行、バックグラウンド実行、Code Mode 経由の実行を含める。人が OpenCode から直接実行する shell コマンドと、MCP ツール内部の実行は含めない。
  - why: エージェントによる事故を防ぐ用途に対象を絞るため
  - decided_by: 利用者（第1ラウンドQ1でAを選択）
- A3 今回の連携で allow・ask・block の全判定を扱う。ask は利用者に確認を求め、block は実行を拒否する。コマンドを付けずに行うリダイレクトによる切り詰めも判定と確認の対象に含める。
  - why: OpenCode がもともと許可している実行でも guardian の確認が省略されないようにするため
  - decided_by: 利用者（第1ラウンドQ2でAを選択）
  - superseded_by: [A7](./2026-10-02-opencode-v2-hook.md#A7)
- A4 OpenCode の権限判断と guardian の判定は厳しいほうを採用する。OpenCode の拒否・確認を guardian の allow で緩和せず、OpenCode が許可していても guardian の ask は確認、block は拒否にする。
  - why: guardian が解析対象にしない危険についても OpenCode の既存の権限判断を維持するため
  - decided_by: 利用者（第2ラウンドQ3の推奨案Aを採用）
- A5 guardian が ask と判定した実行は、その実行ごとに確認する。OpenCode の保存済み許可で guardian の ask を省略しない。
  - why: 同じコマンドでもファイルの追跡状態や変更状態が変わり、以前の許可が現在の状態を保証しないため
  - decided_by: 利用者（第2ラウンドQ4の推奨案Aを採用）
- A6 バイナリ未検出、タイムアウト、無効な応答などにより guardian の判定結果を取得できない場合は、判定できなかった理由を表示して利用者に確認する。連携異常だけで危険と断定して block にせず、黙って実行もしない。
  - why: 判定不能は ask とする既存の方針を維持し、guardian が動かない状態を利用者が認識して判断できるようにするため
  - decided_by: 利用者（第2ラウンドQ5の推奨案Aを採用）
- A7 今回の連携は allow・ask・block の全判定を扱い、コマンドを付けずに行うリダイレクトによる切り詰めも含める。ask は OpenCode の承認フローに渡し、明示的な run --auto による自動承認も有効な承認として扱う。人の承認を追加で強制しない。連携異常時に求める確認にも同じ承認の意味を用いる。OpenCode の保存済み許可で guardian の ask の承認要求を省略しない。block は run --auto でも実行を拒否する。
  - why: run --auto は利用者が確認を省略する意図で指定するものであり、guardian がその意図を変更して人の確認を強制する必要はないため。保存済み許可による判定の省略と、今回生成した承認要求への自動応答は区別するため
  - decided_by: 利用者（Q6への補足回答）
- A8 今回の対応環境は既存の配布対象である Linux x86_64・WSL 上の Bash に絞る。別の shell では安全に判定できたと見なさず、対象外である理由を表示して OpenCode の承認フローに渡す。
  - why: shell ごとの構文差の対応をエージェント連携の追加と同時に広げないため
  - decided_by: 利用者（Q7の推奨案Aを採用）
- A9 利用者が OpenCode のグローバル設定へプラグインを登録する導入手順を主に用意する。今回の作業で個人設定を自動変更しない。
  - why: 普段使う複数のリポジトリで連携を有効にしつつ、個人環境への反映は利用者の操作にするため
  - decided_by: 利用者（Q8の推奨案Aを採用）
- A10 現行 OpenCode V2 の HTTP API による確認要求作成を使う方式を採用し、プラグインをホストする同一サーバーへの明示的な接続・認証設定を受け入れる。接続先を推測せず、必要な設定を導入手順で示す。
  - why: 別プロジェクトの API 拡張を前提にせず、現行 V2 の API で連携を実現するため
  - decided_by: 利用者（Q9の推奨案Aを採用）
- A11 OpenCode 連携も既存の guardian 設定を共有し、影実行の切り替えをプラグイン側に重複させない。mode.enforce が false なら guardian は判定をログに残すだけで、guardian 由来の確認・拒否は出さない。OpenCode 本来の権限判断は維持する。
  - why: OpenCode 専用の設定箇所を増やさず、既存の影実行の運用をそのまま使うため
  - decided_by: 利用者（Q10の推奨案Aを採用）
  - superseded_by: [A23](./2026-10-02-opencode-v2-hook.md#A23)
- A12 OpenCode V2 プラグインは TypeScript で実装する。
  - why: V2のAPIとの型の食い違いを検査でき、JavaScriptをあえて選ぶ理由がないため
  - decided_by: 利用者（Q11でAを選択）
- A13 TypeScriptプラグインをguardianのリリースに同梱し、本体と同じ版で更新する。npmへの別公開は行わず、プラグインの配置・登録手順を用意する。
  - why: npmへの公開・保守を増やさず、本体とプラグインの配布経路を揃えるため
  - decided_by: 利用者（Q12の推奨案Aを採用）
- A14 承認待ちにはプラグイン独自の時間制限を設けず、OpenCodeの承認を待つ。セッション中断・接続断・プラグイン解除では対象コマンドの実行を取りやめ、再接続しても勝手に再開しない。プラグイン独自の承認履歴は保存しない。guardian自体の判定時間上限は維持する。
  - why: 人が判断している間に期限切れにせず、中断後の意図しない実行と追加の保存状態を避けるため
  - decided_by: 利用者（Q13の推奨案Aを採用）
- A15 HTTPサーバーへの接続・認証の失敗などにより承認要求そのものを出せない場合は、対象コマンドを実行せず、接続できなかった理由を返す。guardianが危険と判定したblockとは区別し、承認なしでOpenCode本来の権限判断に委ねて実行しない。
  - why: guardianのaskが利用者や自動承認の経路に届かないまま実行されることを避けるため
  - decided_by: 利用者（Q14の推奨案Aを採用）
- A16 guardianの承認要求を拒否した場合は、同じセッションで保留中の他の承認要求も拒否するOpenCodeの標準挙動に従う。この判断はすでに実行中のコマンドを止める要求ではない。
  - why: guardian独自の拒否方式やOpenCode側の変更を増やさないため
  - decided_by: 利用者（Q15の推奨案Aを採用）
- A17 OpenCode V2のみを対象とし、初回の検証基準は2.0.21にする。V1互換は作らず、後続V2まで検証済みとは扱わない。検証した版を明記する。
  - why: 普段使っている版を基準に初回の検証範囲を絞り、未検証の互換性を保証しないため
  - decided_by: 利用者（Q16の推奨案Aを採用）
- A18 モデルを呼ばない自動試験と、隔離したV2サーバーでの承認APIの連携試験を必須にする。実バイナリの判定、承認前に実行されないこと、拒否・中断・並行実行を確認する。普段のOpenCode設定やセッションは変更しない。モデルを使う実使用試験は任意とする。
  - why: モデル呼出しの料金と実行結果のばらつきを必須の検証へ持ち込まず、判定と承認の実際の連携を隔離環境で確かめるため
  - decided_by: 利用者（Q17の推奨案Aを採用）
- A19 OpenCodeプラグインからRust本体を呼ぶ入口は既存のhookに追加する "hook --agent opencode" とする。設定・影実行・ログは既存hookの処理を使い、OpenCode用の入出力を追加する。checkの手動利用の契約とClaude・Codexの既存hook契約は変更しない。
  - why: プラグインがguardianの設定を読み直す必要をなくし、手動利用の入口への変更を避けるため
  - decided_by: 利用者（Q18の推奨案Aを採用）
- A20 対応する導入環境はBashを明示設定し、他のhookが実行コマンド・cwd・shellを変更しない環境に限定する。任意のhookによる変更後の最終入力まで判定できる保証は付けず、そのためのOpenCode側のAPI拡張を今回の前提にしない。
  - why: 現行V2の公開APIで最終実行入力の一致を無条件に保証できず、上流拡張を求めると対応負担が増えるため
  - decided_by: 利用者（Q20の推奨案Aを採用）
- A21 承認待ち中に通信の終了・エラーを検知した時点で、対象コマンドの実行を取りやめる。通信が無応答になっただけの状態を即座に検知する保証は付けず、接続の生存監視とその閾値設定は追加しない。
  - why: 接続の生存監視の設定と実装を増やさず、検知できる通信失敗に対する保証を明確にするため
  - decided_by: 利用者（Q21の推奨案Aを採用）
- A22 中断と確認要求作成が競合した場合は対象コマンドを実行せず、確認表示の後始末は可能な範囲で行う。競合で確認表示が残っても、後の承認や再接続で実行を再開しない。確認表示を必ず消せるという保証のためのOpenCode側拡張は求めない。
  - why: 現行APIでは競合時の完全な後始末を保証できない一方、実行を再開しないことはプラグイン側で管理できるため
  - decided_by: 利用者（Q22の推奨案Aを採用）
- A23 OpenCode連携は既存のguardian設定を共有し、影実行の切り替えをプラグイン側へ重複させない。本体の応答でmode.enforceがfalseの影実行と確定できた場合だけguardian由来の確認・拒否を出さず、OpenCode本来の権限判断を維持する。確定済みの影実行では、ログ保存失敗と対応外shellは警告にとどめる。バイナリ未検出・タイムアウト・無効な応答で影実行か分からなければ、判定結果を取得できない失敗として承認フローに渡す。ログは既存どおり影実行時だけ記録する。OpenCode用応答は判定の無い影実行と判定不能を区別するが、Claude・Codexの既存hook契約は変更しない。
  - why: 影実行と確定済みの観測では判定を強制せず、影実行か確定できない導入不備ではguardianを黙って外さないため
  - decided_by: 利用者（Q23の推奨案Aを採用）
- A24 対応条件内で、guardianが判定するコマンド本文・cwd・shellと、承認の対象および実際に起動する入力を一致させ、その実行への対応を承認待ちの間も保持する。省略・相対cwd、および同じ本文でcwdが違う並行実行も検証する。一致を確認できない場合は判定不能としてOpenCodeの承認フローに渡す。影実行と確定済みの場合はA23の優先順位を使う。他のhookによる変更と承認待ち中のファイル状態変化まで保証するものではない。
  - why: プラグインの配線や非同期処理によって、判定した対象とは違う場所・実行を開始する不具合を防ぐため
  - decided_by: 利用者（Q24の推奨案Aを採用）

## Evidence

V2 2.0.21 の [permission plugin context](https://github.com/anomalyco/opencode/blob/v2.0.21/packages/plugin/src/promise/permission.ts#L22-L24) は list・get・reply と評価hookを公開するが、確認要求の作成は公開しない。
同版の [HTTP API](https://github.com/anomalyco/opencode/blob/v2.0.21/packages/protocol/src/groups/permission.ts#L63-L86) には確認要求の作成があり、[handler](https://github.com/anomalyco/opencode/blob/v2.0.21/packages/server/src/handlers/permission.ts#L39-L57) はネイティブの permission.ask を呼ぶ。これを使う連携には自身をホストするサーバーへの接続・認証が必要であり、連携そのものは未実機検証である。
同版の [非対話CLI](https://github.com/anomalyco/opencode/blob/v2.0.21/packages/cli/src/run/noninteractive.ts#L158-L185) は auto が有効なら確認要求へ once を自動返信し、無効なら拒否する。確認要求を出すだけでは、人が承認したことを保証できない。
[V2のプラグイン設定ドキュメント](https://opencode.ai/v2/docs/plugins) は.tsと.jsのローカルプラグイン、およびローカルディレクトリと公開パッケージを読み込む方式を示す。プラグインの提供にnpmへの公開は必須ではない。
V2 2.0.21 の [shell起動処理](https://github.com/anomalyco/opencode/blob/v2.0.21/packages/core/src/shell.ts#L254-L275) はツールラッパーより後で可変のshell起動前hookを実行する。[cwdの解決](https://github.com/anomalyco/opencode/blob/v2.0.21/packages/core/src/file-access.ts#L66-L76) は字句的な絶対パスへの解決であり、プラグインが事前に実パスへ変換した文字列と同一とは限らない。
同版の [plugin contextのreply](https://github.com/anomalyco/opencode/blob/v2.0.21/packages/core/src/plugin/host.ts#L404-L426) は内部のpermissionサービスを呼ぶため、独立したHTTP接続が切れても既知の保留要求を拒否できる。ただし要求作成と中断の競合時の完全な後始末、および通信エラーとして現れない接続断の即時検知は未保証である。
