# CLI language and help

## Context

利用者は CLI の日本語出力が不自然であるため、英語への変更を求めている。
使い方を利用者が確認できるよう、"--help" も整備したい。
既存のヘルプの有無と出力経路を調べ、翻訳対象とヘルプの範囲を明示してから修正する。

Position: A1〜A10 は利用者承認済み。追加合意の出典を IR 草稿へ反映し、最終照合に返す準備ができた。仕様草稿の承認待ちであり、実装は未着手。

## Agreements

- A1 CLI の製品が生成する説明を英語にし、利用者がヘルプから使い方を確認できるようにする。
  - why: 日本語の不自然な説明と使い方の分かりにくさを改善する
  - decided_by: 利用者

- A2 製品が生成する通常出力、エラー、警告、JSON の説明、hook の拒否理由を英語に統一する。利用者が設定した "reason" とコマンド本文は変更せず保持する。
  - why: 同じ説明が出力経路によって別の言語にならないようにし、利用者が指定した文言を勝手に翻訳しないため
  - decided_by: 利用者（推奨を採用）
- A3 トップレベルと各サブコマンドで "--help" と "-h" を提供する。用途、引数、オプション、使用例、終了コードを英語で表示し、ヘルプ表示は成功終了にする。
  - why: 利用者がコマンドの入口と個別の使い方を製品自身から確認できるようにするため
  - decided_by: 利用者（推奨を採用）
- A4 ヘルプは標準出力へ表示し、終了コード 0 にする。設定読込、コマンド判定、標準入力の読取を行わない。"check -- '--help'" のように "--" 以降に渡した文字列は、ヘルプではなく判定対象として扱う。
  - why: ヘルプを入力や設定に依存せず表示し、判定したい文字列とオプションを区別できるようにするため
  - decided_by: 利用者（推奨を採用）
- A5 利用者指定の "reason"、パス、規則名、コマンド本文、OS やライブラリ由来のエラー詳細はそのまま保持する。JSON のキーと終了コードは変更せず、製品が付ける説明だけを英語にする。
  - why: 翻訳によって入力データや外部エラーの情報を損なわず、既存の機械向け契約を維持するため
  - decided_by: 利用者（推奨を採用）
- A6 "check" の "--cwd" 省略時は現在の作業ディレクトリを使い、"hook" は標準入力から入力を受け取る。これらの既存動作を維持し、ヘルプでも説明する。
  - why: 現行の入力経路と既定値を明示し、ヘルプと実際の使い方を一致させるため
  - decided_by: 利用者（推奨を採用）
- A7 カスタム規則の名前の保持と、見張り規則の利用者指定 "reason" の保持を、既存の二種類の規則を使った別々の例で確認する。名前と利用者指定理由を同時に持つ新しい設定項目は追加しない。
  - why: 翻訳の検証例を成立させるために既存の設定契約を拡張しないため
  - decided_by: 利用者（推奨を採用）
- A8 改行を含む利用者・外部由来の文字列は元のデータを保持し、2 行から 4 行の製品説明に埋め込む際だけ、改行を "\n" のようなエスケープ表記で表示する。削除、切り詰め、単一行への入力制限は行わない。
  - why: 入力の情報を保持しながら、非 allow の文面の行数契約も満たすため
  - decided_by: 利用者（推奨を採用）
- A9 影実行は既存の "mode.enforce=false" で指定する。判定を返さず、理由とコマンド本文を影実行のログに記録する既存動作を維持する。
  - why: 古い決定記録の "shadow" 表記と現行の設定値との対応を明示するため
  - decided_by: 利用者（既存動作の維持を承認）
- A10 JSON の "rules[].reason" は一致した見張り規則の利用者指定理由を、元の改行を含めて保持する。"message" は表示用の製品説明であり、そこに埋め込む改行だけをエスケープする。新しい JSON キーや設定項目は追加しない。
  - why: 元データを格納する既存の出力と表示用説明との違いを明示し、翻訳と行数の検証を可能にするため
  - decided_by: 利用者（既存の JSON 契約の維持と表示時の改行処理を承認）
