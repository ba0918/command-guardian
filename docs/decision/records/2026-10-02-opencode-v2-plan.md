# OpenCode V2 連携の実装計画の方式

## Context

OpenCode連携の仕様はコミット97b046e86ac0507cccbf72c5dd5d475a56274393で承認済みである。
実装担当が同じ検証を再現できるよう、作業順序・試験コマンド・変更対象を計画で固定する。
ここで記録するのは製品の挙動を変えない開発上の方式であり、プラグインの具体的な入出力と接続設定は既存の委譲範囲に残す。

Position: 実装計画と合わせて利用者の承認待ち。製品実装は未着手。

## Agreements

- A1 TypeScript側の開発はBunの既存のプロセス実行・テスト機能とTypeScriptの型検査を使い、依存をロックして再現する。公開APIの型とHTTP通信はV2 2.0.21の公式プラグイン・クライアントを先に採用候補とし、型検査と隔離試験で確認する。配布するプラグインにBun固有APIを必要とするかはホスト実行環境との適合を確認してから決める。
  - why: 上流の同版もBunで試験しており、追加のテストフレームワークや独自HTTPクライアントを避けられるため。開発用ランナーと導入先のホストを混同しないため
  - decided_by: 計画担当。既存の[委譲範囲](./2026-10-02-opencode-v2-hook.md#D1)内の開発方式として提案
- A2 プラグインの実装・試験・開発用manifestは "plugins/opencode/" にまとめる。試験はunitとintegrationの別コマンドにし、後者も必須とする。実バイナリと隔離サーバーの場所を試験へ渡し、既存のOpenCodeサービスを発見・起動・停止するAPIは使わない。
  - why: Rust側とプラグイン側の境界を一か所で追え、個人環境への副作用を避けた検証を再現できるため
  - decided_by: 計画担当。既存の[隔離検証の決定](./2026-10-02-opencode-v2-hook.md#A18)を実行可能な工程にするため
- A3 ".kotowari/config.yaml" の試験と変更対象へプラグインのTypeScript・manifest・lockfileを加える。TypeScriptの試験には既存の汎用印を使い、新たな解析器を自作しない。生成物と依存展開先は変更対象にしない。
  - why: Rustだけを列挙する現在の設定では、プラグインの変更と要求に対応する試験を検査できないため
  - decided_by: 計画担当。プロジェクト既存の変更照合を新しい実装言語にも適用するため
- A4 配布物の組立てはCIとローカル検証が同じスクリプトを使い、作成したアーカイブの中身で同梱を確認する。今回は公開・タグ作成・個人のグローバル登録を実施せず、CHANGELOGはUnreleasedに記録する。
  - why: 配布工程を公開前に検証し、外部公開と個人環境への反映を実装から分離するため
  - decided_by: 計画担当。既存の[同梱配布](./2026-10-02-opencode-v2-hook.md#A13)と[個人設定を変更しない決定](./2026-10-02-opencode-v2-hook.md#A9)の範囲内

## Delegated

- D1 "plugins/opencode/" の内部ファイル名、公開されていない内部型、試験用fixtureの配置は実装担当に委ねる。プロトコルと接続設定の具体化は既存の[委譲範囲](./2026-10-02-opencode-v2-hook.md#D1)で根拠とともに記録する。
  - why: 振る舞いを変えないファイル分割まで計画で固定する必要がないため

## Rejected

- R1 普段使うOpenCodeサービスへの接続を必須試験に使う案。
  - why: 個人設定・セッションを変更しない承認済みの境界に反するため
