# guardianのaskを自動で許可へ倒す任意設定

## Context

guardianの`ask`は、エージェントの承認フローで人の確認を求める。
OpenCodeの"run --auto"やClaude Codeの自動系の権限モードのように、確認を挟まず進めたい利用者がいる。
利用者は、推奨はしないが明示的に有効化したときだけ`ask`で確認を求めず、エージェント側の判断に委ねる任意機能を求めた。
`block`の扱い、設定の層、適用する入口、記録の有無を決める必要がある。

Position: 第1ラウンドでA2〜A9、第2ラウンドでA10〜A13、第3ラウンドでA14〜A15、第4ラウンドでA16〜A17を決定した（すべて推奨を採用）。IRを記述し、敵対的レビューの指摘を反映し、照合を3回で完了した（未裏付け0件）。未決定は無い。承認・実装済みで、0.3.0で配布した。Claude Codeのauto時のask挙動は公式文書で確認し、A1の根拠に加えた。

## Agreements

- A1 有効化したとき、guardianは`ask`を`allow`へ変えるのではなく、エージェントへ何も返さず、確認の要否をエージェント本来の権限判断（Claude Codeのautoモードの判定、OpenCodeの"run --auto"や保存済み許可など）に委ねる。guardianが許可を出すことはしない。
  - why: エージェント側の自動モードと同じ作用を得つつ、guardianが安全と判定したことにはしないため。許可を出さないので、権限判断を弱めないREQ-049の考え方と衝突しない
    Claude Codeの公式文書（https://code.claude.com/docs/en/hooks 、2026-10-04確認）は、フックの"ask"はautoモードでも確認を強制し分類器は黙って承認できないこと、何も出力しない終了コード0は通常の権限フローへ進み承認にはならないことを述べている。
  - rejected: `ask`を`allow`の判定へ変える案、guardianの助言に`ask`の可否を判定させる案
  - decided_by: 利用者
- A2 委任の対象は最終判定が`ask`のものすべてとする。パス分類、読めない構文の判定不能、カスタムルール、guard規則、助言で`ask`になったものを含む。`block`は委任せず従来どおり拒否する。
  - why: エージェント側の自動モードと同じく「確認を挟まない」という単純な意味にするため。読めない構文も委任される危険はREADMEで警告する
  - decided_by: 利用者（推奨を採用）
- A3 委任は利用者設定の`mode.defer_ask = true`でだけ有効にでき、既定はfalseとする。プロジェクト設定にあれば、信頼済みプロジェクトでも無視して警告する。
  - why: リポジトリ側のファイルが確認を黙って外せると、guardianの意味が失われるため
  - decided_by: 利用者（推奨を採用）
- A4 委任はフックの入口だけに適用する。`check`は本来の判定と終了コードを返す。Codexの出力は従来どおり変わらない。
  - why: `check`は判定を確かめる道具であり、本来の判定が見えなくなると困るため
  - decided_by: 利用者（推奨を採用）
- A5 OpenCodeでは、委任した`ask`についてguardian由来の承認要求を出さず、OpenCode自身の権限判断だけで進める。`block`の拒否と判定結果を取得できない場合の扱いは変えない。
  - why: A1の委任をOpenCodeの承認フローで具体化するため
  - decided_by: 利用者（推奨を採用）
- A6 委任した実行は、影ログと同じ保存先に、本来は`ask`でエージェントへ委任したと分かる行として記録する。保存に失敗しても警告して処理を続ける。
  - why: 推奨しない機能なので、何を素通しにしたかを後から追えるようにするため
  - rejected: 記録しない案、専用の別ファイルに書く案
  - decided_by: 利用者（推奨を採用）
- A7 影実行（`mode.enforce = false`）を委任より優先し、影実行の挙動は変えない。
  - why: 影実行は何も強制しない観測用のモードで、委任を重ねる意味がないため
  - decided_by: 利用者（推奨を採用）
- A8 助言は委任時もそのまま動かす。助言で`block`になったものは拒否し、`ask`になったものは委任する。
  - why: 助言の`block`を委任時にも残る安全網にするため
  - decided_by: 利用者（推奨を採用）
- A9 委任時にエージェントへ補足（guardianが確認を求めたかったこと）を渡さず、何も返さない。
  - why: 新しい出力の契約を増やさないため。またautoモードの判定が補足を読むかは確認できていないため
  - decided_by: 利用者（推奨を採用）

- A10 委任の記録行には、影ログと同じ項目（時刻、判定、理由、対象パス、コマンド本文）に加え、委任の行と影実行の行を見分ける印を入れる。印の具体的な書き方は実装担当が決め、READMEに契約として記載する。
  - why: 同じファイルに種類の違う行が混ざっても、後から分けて読めるようにするため
  - decided_by: 利用者（推奨を採用）
- A11 `mode.defer_ask`が有効なら、入口と権限モードに関係なく、フックで委任した`ask`をすべて記録する。Claude Codeの"dontAsk"・"bypassPermissions"とCodexのように、もともと`ask`で何も返さない場合も含む。無効なときは従来どおり記録しない。
  - why: 有効化した利用者が、素通しにしたものを一か所でまとめて追えるようにするため
  - decided_by: 利用者（推奨を採用）
- A12 OpenCode用の応答では、委任を許可と別の値として返す。プラグインはどちらでもguardian由来の承認要求を出さない。JSONの具体的なキーと値は、REQ-048と同じく実装担当が契約として記録する。
  - why: プラグインは設定を読み直さないため委任は本体の応答で伝える必要があり、区別しておけばテストで委任の経路を確認できるため
  - decided_by: 利用者（推奨を採用）
- A13 有効化中であることは判定ごとには知らせず、READMEの英語版と日本語版に、推奨しない理由と危険（読めない構文や判定できない場合も委任されること）を記載する。
  - why: 判定ごとの警告はエージェントの画面を騒がしくするうえ、有効化には利用者が自分で設定を書く必要があるため
  - rejected: `check`の出力にフックでは委任される旨を注記する案
  - decided_by: 利用者（推奨を採用）

- A14 判定の内部エラー、gitの失敗、解析の失敗による`ask`（REQ-010）も、理由を区別せず委任する。OpenCodeプラグインが本体の判定結果を取得できない場合（REQ-051）はguardianの`ask`ではないため委任せず、従来どおり承認を求める。
  - why: 委任の対象を「最終判定が`ask`のもの」と一言で説明できるようにするため。委任後もエージェント側の判定とdenyルールは働く
  - decided_by: 利用者（推奨を採用）
- A15 プロジェクト設定の`mode.defer_ask`は型の検証前に取り除いて警告し、型や値が不正でも同じファイルの他の設定を不採用にしない。利用者設定の`mode.defer_ask`の型や値が不正なら、REQ-015どおりそのファイル全体を不採用にして警告し、委任は無効のままにする。
  - why: プロジェクトでは無視するキーの誤りで保護規則を失わず、利用者の書き間違いでは委任が有効にならない安全側へ倒すため。助言の"advisor"節と同じ扱いにそろえる
  - decided_by: 利用者（推奨を採用）

- A16 判定に至らなかったフックの失敗（フックの入力をJSONとして読めない場合を含む）は委任に含めず、Claude CodeとCodexの従来の扱いに従い、委任の記録も書かない。
  - why: 委任の対象は最終判定が`ask`のものであり、判定が無いものは範囲外であるため。記録に必要なコマンド本文や対象パスも得られない
  - decided_by: 利用者（推奨を採用）
- A17 OpenCodeで委任の記録の保存に失敗しても、委任の応答は変えない。保存失敗は警告として応答に含め、プラグインは警告として示すだけで承認要求を出さず、無効な応答として扱わない。
  - why: 影ログの保存失敗を警告にとどめる既存の扱いとそろえ、警告付きの応答が判定不能の経路に流れて承認要求が出ることを防ぐため
  - decided_by: 利用者（推奨を採用）

- A18 委任の記録行は、影実行の行と同じ5つのタブ区切りの欄（時刻、判定、理由、対象パス、コマンド本文）の後に、6番目の欄として`deferred`を足す。判定の欄は`ask`のままにする。影実行の行は5欄のまま変えない。
  - why: 既存の影実行の行の形を変えずに、欄の数と最後の欄で委任の行を見分けられるようにするため。コマンド本文のタブはエスケープ済みなので、欄の数は一意に決まる
  - rejected: 判定の欄を`deferred-ask`などに変える案（判定の値が`allow`・`ask`・`block`以外になる）、先頭に印の欄を挟む案（委任の行で既存の欄の位置がずれる）
  - decided_by: 実装担当。A10の委任の範囲
- A19 OpenCode用の委任の応答は`{"status": "deferred", "mode": {"enforce": true}, "reason": <理由>}`とし、"verdict"を含めない。記録の保存に失敗したときは`"warning": <文字列>`を足す。プラグインは、"mode.enforce"がtrueで"verdict"が無く、"warning"が無いか文字列のときだけ委任として扱い、それ以外の"deferred"の応答は無効な応答として承認を求める。
  - why: judged・shadow・unavailableの既存の応答の形と分類を変えず、allowと取り違えない別の"status"にするため。古いプラグインは未知の"status"を無効な応答として承認を求めるので、安全側に倒れる
  - rejected: judgedの"verdict"に`deferred`を足す案（judgedの"verdict"は判定の値だけというA2の形が変わる）
  - decided_by: 実装担当。A12・A17の委任の範囲

## Rejected

- R1 `ask`を`allow`の判定へ変える案。
  - why: guardianが安全と判定したことになり、記録と意味が実態と食い違うため
  - decided_by: 利用者
- R2 guardianの助言（LLM）に`ask`を`allow`か`block`へ決めさせる案。
  - why: 助言は機械判定を緩めないという既存の原則を覆すことになり、影響が大きすぎるため
  - decided_by: 利用者
